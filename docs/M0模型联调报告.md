# M0 模型联调报告

日期：2026-09-14。结论：本机 HY-MT2 与 WhisperKit 已能执行真实推理，录音文件的转写、翻译、时间轴及检查点保存链路已跑通。当前仍有明确的条件误译和窗口边界问题，未通过真实课堂质量或实时麦克风验收，M0 尚未完成。

## 环境与资源

- Apple M5 Pro / 48GB，macOS 26.6.2，Swift 6.3.3；当前为 Debug 命令行构建。
- Ollama 0.33.3，使用 Metal；本次启动的测试服务仅监听 `127.0.0.1:11434`，`OLLAMA_NO_CLOUD=1`，同一时刻最多驻留一套文字模型。未更改用户全局 Ollama 配置。
- 用户已有 `hy-mt2:1.8b-q8`（约 1.91 GB）与 `hy-mt2:7b-q8`（约 7.98 GB），均为本地 Q8_0 模型。
- 用户已有 Whisper `openai_whisper-small.en`（约 464 MB）和 `openai_whisper-large-v3-v20240930_turbo`（约 1.5 GB）的 Core ML 资源。
- 两套分词器原本缺少 `tokenizer.json`；本次分别从 `openai/whisper-small.en`、`openai/whisper-large-v3-turbo` 补齐约 2.41 MB、2.71 MB 的文件。未重新下载语音权重。下载元数据记录的 revision 分别为 `e8727524f962ee844a7319d92be39ac1bd25655a`、`41f01f3fe87f28c78e2fbf8b568835947dd65ed9`。
- 生成并通过语音文件 SHA-256 清单校验；清单不包含隐藏下载缓存。WhisperKit 使用已固定的本地分词器补丁，模型加载设置 `download: false`。

模型准备阶段使用了网络。实际推理使用回环服务和本地 Core ML 文件，但本轮没有断开外网，也没有进行进程级网络审计，因此不能据此宣称完整离线验收通过。

## 代码调整

1. HY-MT2 使用腾讯模型卡的用户消息格式、术语提示和 1.8B/7B 推荐参数：temperature 0.7、top_p 0.6、top_k 20、repeat_penalty 1.05；程序上下文上限 8192、输出上限 4096。默认再加入数字、条件、时间界限、统计限定词和段落保真要求，报告标识为 `hy-mt2-faithful-v1`。
2. 仅向声明支持 thinking 的模型发送 `think: false`；仍拒绝非本机端点和云模型元数据，不自动拉取模型。
3. 文字报告增加提示方案、模型加载、输入计算、生成耗时。语音报告分开记录资源加载与处理耗时，避免仅报 ASR 速度。
4. 语音清单忽略隐藏缓存，拒绝枚举到的未完成文件；片段时间戳限制在当前音频窗口内。哈希校验不是译文质量验证。
5. 新增 [本地 Ollama 启动脚本](../scripts/ollama-local.sh) 和 [M0 一键集成测试脚本](../scripts/m0-smoke.sh)。后者默认合成英语，也可接受用户短录音；没有麦克风采集。

## 文字实测

材料为项目的 [英语样本](../fixtures/translation-en.txt) 和 [中文样本](../fixtures/translation-zh.txt)。英语样本共 69 个按空白分隔的词，含申请期限、退款条件及统计结论。每种模型执行首次英译中、重复英译中、一次中译英。请求串行，未与其他测试推理并发。

| 模型 | 首次英译中总耗时 | 其中模型加载 | 重复英译中总耗时 | 重复请求首字 | 中译英总耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| HY-MT2 1.8B Q8 | 1.505 秒 | 0.561 秒 | 0.857 秒 | 0.019 秒 | 0.757 秒 |
| HY-MT2 7B Q8 | 4.978 秒 | 1.047 秒 | 3.572 秒 | 0.047 秒 | 2.801 秒 |

计时为生成 API 请求，不含之前的模型元数据检查。首次请求时模型需要重新驻留，但磁盘/系统缓存不保证全冷；重复请求使用相同原文，可能受提示缓存影响。这不是任意新文本的稳定延迟，也不能从两份材料推出准确率或模型排名。

人工检查发现：

- **1.8B 的退款期限存在严重误译。** `at least 14 days before the course begins` 在一次输出中成为“至少在课程开始前14天以内”，方向含混并可能反转条件。重复请求改成“至少提前14天”，说明一次得到正确结果仍不能证明稳定。
- **7B 仍改变业务条件。** `the cancellation is received` 被译为“提出取消申请”；“收到”与“提出”可能对应不同日期。较大的模型也未通过严格保真检查。
- 初始仅使用官方基本提示时，7B 中译英曾漏掉“每天”扣分、英译中曾遗漏“平均”的限定。加入通用保真要求后，本轮保留了这些限定，但上述“收到/提出”和 1.8B 期限问题仍在。没有将提示词优化当作修复保证。
- 自动数字检查会因 `September` → `9月`、英文数字词 → 阿拉伯数字产生提示；它也无法检测“收到/提出”等语义差异。无警告不代表没有严重错误。

阶段性选择：1.8B 作为低延迟候选，7B 作为质量比较候选。先保留两者供 M0 对照，尚不确定最终默认模型；当前尚未通过课程通知和退款条件等文本的保真检查。

## 语音和完整双语链路

使用系统已安装的 Samantha 英语语音，以 155 的朗读速率生成上述英语材料。音频长 **26.113 秒**，单声道 22.05 kHz，程序转为 16 kHz。它是清晰合成样本，不能代表口音、远距离、多人或课堂背景噪声。

| 路径 | 资源校验/加载 | 音频处理或回放阶段 | 加载加处理总时间 |
| --- | ---: | ---: | ---: |
| small.en 仅英文转写 | 18.065 秒 | 1.293 秒 | 19.359 秒 |
| turbo 本轮首次英文转写 | 114.048 秒 | 1.709 秒 | 115.758 秒 |
| turbo + 1.8B 英中双语 | 1.659 秒 | 3.371 秒 | 5.031 秒 |
| turbo + 1.8B 按原时长回放 | 1.657 秒 | 28.001 秒 | 29.659 秒 |

首次 turbo 加载可能涉及 Core ML 的设备专用准备，本次未将每项内部操作单独剖析；后续加载明显变快，应用应提前准备并复用已加载实例。不能把 1.709 秒转写速度当作首次使用总耗时。双语处理计入音频读取、转换、ASR、逐片段翻译和检查点保存，最终 JSON 落盘在总时间记录之后；尚未包括录制、播放和字幕导出。

两个引擎均发现了现有约 15 秒独立窗口的局限：

- small.en 将切在窗口边界的句尾补为 `received as a result`，其中 `as a result` 不存在于原文。
- turbo 未出现同样补词，但把“取消申请收到”与“至少提前14天”分到不同窗口，还把多个句子合为一个时间段。
- 每个 ASR 片段立即独立翻译，导致中文进一步误解被截断的退款条件。保留两个相邻 JSON 片段不足以恢复句意。

回放共得到 4 个片段，按模型时间戳计算的落后时间约 1.54–7.96 秒，但第一个结果要在回放开始约 **16.54 秒**后才出现，且包含多句话。时间戳未经独立标注，样本也很短，因此这些数字不作为实时分句字幕的延迟验收，更不能从 4 个片段推断 P95 或长期积压趋势。

## 下一步的实施边界

1. **先改语音分句与稳定提交。** 加入语音活动检测、带重叠的滚动窗口、时间轴对齐和去重；未完成的句子保留到下一窗口，完整稳定句子再交给翻译；停止时冲刷尾句。用本次跨 15 秒退款句作为回归样本，再加入长停顿、连续不停顿和重复语句。
2. **接入真实麦克风最小窗口。** 显示英文草稿、稳定英文和对应中文；采集与推理分离，保存原音频，限制队列积压；先跑 5–10 分钟，再测课堂距离、口音、暂停和设备中断。此阶段才开始验证用户要求的边录边显示分句字幕。
3. **扩充真实文字初筛。** 首批约 30 条来自实际学习生活的中英材料，覆盖日期边界、收到/寄出、每日/每次、否定、退款、术语和段落上下文。记录每个候选的严重误译和人工修正成本，不能只依赖数字正则或单个标准答案。
4. **继续文档和完整验收。** 用实际 PDF/课件/Word 验证结构及来源，再进行断网后新输入、60–90 分钟持续运行、资源缺失、中断恢复、回放及双语字幕导出。当前尚未测峰值内存与能耗，也未实现自动续跑。

这些工作继续属于 M0。资源已够开展下一轮，不需要先扩大模型下载范围；最终模型和实时处理方案由以上实测决定。
