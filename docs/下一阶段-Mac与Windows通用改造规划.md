# Mac 与 Windows 通用改造规划

编制：2026-10-03；硬件补充：2026-10-04。用户新增目标：同一产品在 Mac 和 Windows 使用。用户提供 **Windows 11 x64、AMD Ryzen 7 8845H、32GB内存、两块各1TB固态硬盘、NVIDIA GeForce RTX 4070 Laptop GPU**；独立显存和驱动版本尚未提供，规格及各卷剩余空间待开机实机核对。Windows电脑目前已关机，已有SSH及登录自动准备验证保留，见[协作说明](跨设备接续与Windows测试协作说明.md)。本文为源码核查后的规划，未启动移植、下载、安装、模型转换或 Windows 构建/验收。

当前仅交付Apple Silicon/macOS26及以上的0.2.10/build46。下一轮主任务调整为[统一跨平台架构与Windows适配](下一阶段-统一跨平台架构与Windows适配任务书.md)，Mac发行收尾作为[共同交付子任务](下一阶段-联网发行与生命周期收尾任务书.md)保留。最新跨平台目标覆盖旧规划“多平台暂缓”的平台范围，不恢复质量深调、Office整篇、复杂版面、术语库、完整资料库、快捷阅读、课堂长测等其他暂缓内容。

实施方式进一步细化为[12批子任务](下一阶段-跨平台分批任务安排.md)，配套[分批启动提示词](下一阶段-跨平台分批启动提示词.md)。下方W0—W4为概念阶段，不代表一次连续执行；按指定批次交付并更新共同矩阵，许可预检随依赖引入开展，最终闭环和发布分别验收。

## 1. 通用目标与范围

通用指两平台具备相应功能、采用兼容的任务与结果格式，遵循同一翻译/保存/恢复规则。Mac 和 Windows 分别发行应用、运行包和安装器；不是同一可执行文件跨系统运行，也不承诺不同 GPU 逐字相同输出、相同内存或相同速度。

Windows 首阶段平台为 Windows11 x64；Windows ARM、老系统、Intel Mac、Linux、AMD/Intel GPU 的实时语音支持不自动纳入。具体最低内存/显存和驱动由硬件实测确定，不凭显卡品牌承诺实时吞吐。资源不足明确说明，不自动换小模型、降精度/上下文或关实时功能。

能力分阶段就绪：文字与任务读取/导出先行；文档/PDF/OCR适配；文件语音和录后校对；最后麦克风实时与设备/权限/休眠验收。尚未实现的功能明确显示未就绪；最终全功能通用交付须覆盖当前已交付且未被用户跳过的主流程。

任务可搬动/互读，不增加云同步、自动后台监听或新账号。用户显式传输自己的任务和外部资源；模型数据、录音及数据库继续不入 Git。

## 2. 当前平台绑定与必要改动

| 领域 | 当前代码/平台绑定 | 通用改造 |
| --- | --- | --- |
| 界面 | TranslatorApp 使用 SwiftUI/AppKit，Package.swift 只声明 macOS26 | 下一轮选择共享界面主路线并逐步迁移两端；现有Mac界面保留为稳定基线，平台接口和旧任务按阶段接回 |
| 翻译和任务规则 | 长文/文档状态、分段、recipe/binding在 Swift；字幕/录音SQLite与调度在 Python | 先建立版本化契约与跨语言夹具；逐步将可共用规则抽为独立核心，避免 Windows 独立复制后分叉 |
| 语音实时 | asr.py显式导入MLX，MLX编码/PyTorch MPS FP32解码；资源与自检硬编码MPS/MLX | 抽后端接口；Mac固定组合保持；Windows另建CUDA编码/解码候选，保留SimulStreaming确认、VAD、时间证据和安全保存语义，真实验证可行性 |
| 录后校对 | refine.py调用mlx_whisper整段本地推理 | Windows新增本地CUDA校对实现，仍创建独立子任务、不覆盖原字幕；参数/精度/词时间证据另登记 |
| OCR | DocumentOCR/Importer使用Vision | Mac保留Vision；Windows评估原生OCR是否满足英中、离线与包内资源条件，不满足时再评估可分发离线库；执行库与语言/model数据分离 |
| PDF | PDFKit提取、渲染和原页定位 | Windows选择经许可核查的本地PDF提取/渲染库，保留页序/范围/原页核对；提取器不同不能重排旧任务计划 |
| 采集与回放 | AVAudioEngine、AVFoundation及Apple权限 | Windows用WASAPI或经验证音频封装，保持PCM格式、采样转换、连续落盘、有界缓冲、设备状态和停止排空；Windows权限/休眠单独验收 |
| 安装与运行包 | macos-arm64、Mach-O、签名、.app/DMG；内置Swift安装器 | 平台/架构独立可信清单与安装实现，Windows嵌入解释器/固定DLL及CUDA依赖；独立临时区、校验和原子激活/回退规则共用 |
| 进程控制 | POSIX信号、lsof、Mac目录与可执行身份检查 | Windows命名互斥/文件锁、进程句柄/创建身份、Job Object或等价约束、端口归属与协作取消；先安全收尾，再有界强制结束本应用子进程 |
| 文件与任务定位 | Mac支持目录、POSIX realpath/链接、历史绝对路径 | Windows用户数据目录，处理盘符/UNC/大小写、长路径、重解析点、打开文件替换和权限；内容hash优先，路径变化不豁免digest |

Ollama 本机 HTTP API、HY-MT2 模型身份、翻译 recipe、部分 Python 数据/字幕逻辑可复用，但官方引擎、安装包、GPU运行组件与来源清单仍需按平台重新核对。不能把 Mac 测试结果直接标成 Windows 通过。

## 3. 推荐的架构和界面路线

推荐路线调整为 **共享界面 + 共享任务核心/操作协议 + 平台适配层**，在下一轮先确定并建立共同架构。现有Mac SwiftUI程序保留为稳定基线和核对入口；共享界面评估Qt6/PySide6与Tauri后选定主路线，比较安装体积、内存、字体/长列表、PDF/音频集成、运行依赖及许可证，不因列候选而立即下载或锁定版本。

Mac侧 Swift 纯逻辑并非全部不能移植，但当前 TranslatorCore目标包含WhisperKit、PDFKit、Vision和AVFoundation依赖，不能把整个目标直接作为Windows库构建。先拆纯规则与平台适配，再决定共享核心落在Python、独立Swift子库或其他契约实现中。Python已承载语音/字幕，可优先承接共享worker；尚在Swift中的文本规则需用冻结夹具逐步对齐，不能直接复制后宣称单一核心。

建议结构：

```text
共享桌面界面（分别构建Mac/Windows）
                │
      版本化本地操作协议 ─ 任务/recipe/调度/恢复核心
                                       │
                       Mac/Windows平台适配：推理、OCR/PDF、音频、安装、文件
```

界面与worker优先采用带版本/操作身份的标准输入输出或等价受控IPC；不为共享核心新增公开HTTP服务。协议必须表达就绪、启动确认、进度、取消、安全收尾、错误和结果归属；保留现有真实启动确认/30秒保护与录音有界背压。若需变更启动阈值，应以新平台实测登记，不悄悄放宽旧保护。

统一界面要求将Mac权限、音频和文档入口重接并重验。按最小闭环到文档/语音的阶段迁移，每阶段保留旧Mac可用程序；下次共同功能更新维护同一套界面与规则，平台差异仅在适配层与能力矩阵登记。

## 4. 语音与GPU：最大的技术改造

当前MLX/MPS组合依赖Apple GPU路径，Windows NVIDIA对应CUDA，需要独立后端。优先评估固定Whisper large-v3-turbo、PyTorch CUDA、原SimulStreaming/AlignAtt/VAD确认规则的组合，作为新适配实现；是否能沿用封存实现的接口须检查并作有限真实原型验证。

- 保留Mac已有精度、权重、模型和识别配置。Windows以明确登记的FP32候选进行初验，编码与解码精度分别记录；不默认半精度、量化、较小模型、减上下文或降低采样率。
- 优先复用内容相同的模型张量；MLX资源不能仅凭模型名作为CUDA资源证明。必要格式转换另建外部受控副本，记录来源hash、键/形状/数值/精度及转换版本，保留原资源，不自动下载替代模型。
- Windows backend/runtime/resource各有身份。CUDA与MPS计算不同，禁止承诺逐token一致；验证确认进度、时间映射、尾部、取消/恢复和有限样本差异，不恢复全面模型评选或质量深调。
- 录后校对是独立实现与验收项，不因实时识别可用就标通过。保持原任务、子任务关系及原录音内容证据。
- Windows固定PyTorch/CUDA/ONNX/PyAV组合依据实际兼容性建立，不强求使用不存在的Mac同版本wheel，也不为Windows准备升级Mac已验证组合。
- CPU可作为明确单独标识的离线文件处理候选，不能静默回退或宣称达到实时要求。NVIDIA显存不足时同时计入ASR、Ollama权重与实际并存情况；串行计算不等于模型不同时驻留。

首次Windows短验证至少包括同一短音频、录后校对、字幕补译、安全取消/尾部保存、退出无残留及重新加载；测量工作集/私有内存、GPU分配/显存、冷暖时间及吞吐，口径与Mac分列，不直接把Windows工作集和Mac RSS当成严格相同指标。

## 5. 文档/OCR与媒体适配

PDF适配先保证当前文字层、显式整页OCR、连续页范围、原页阅读和已有任务能力，不恢复复杂排版/Office整篇。Windows新PDF库的许可、中文字体、页面渲染、加密/损坏文件与内存边界独立检查；不能默认采用许可证不匹配的库。

Windows原生OCR候选须证实Win32桌面调用、离线语言资源、英中识别和可控来源。语言包未装时明确缺失；若需独立OCR执行库或模型，先审查许可/实际分发条件并登记外置数据，不能隐式依赖系统临时在线补齐。Mac继续Vision，OCR引擎版本和识别结果来源单独保存，不重写已校正原文。

音视频解码可复用PyAV抽象，但必须构建/取得Windows固定库和DLL依赖闭包，完成对应源码/编解码许可检查；不新增要求用户自行安装FFmpeg、Python或编译器的前提。回放、暂停/继续、采样转换与WAV保存均需Windows实机验证。

## 6. 任务互读和跨平台继续

保持TextDocuments schema1 current/previous/source、base64/checksum、旧v1 contextVersion省略规则；保持SQLite schema3、实际recipe/digest、源修订、lease与binding保护。共同夹具验证两端编码/读取，特别是UTF-8/换行/浮点/JSON字段顺序与哈希输入；不能因解析库不同静默重算身份。

用逻辑资源身份、受控相对定位和内容hash处理Mac/Windows目录差异。旧绝对路径作为证据保留，不覆盖旧runtime.json或以路径变化跳过检查点校验。支持显式导入任务副本，避免两端同时写一份数据库；复制SQLite任务须完成安全提交/关闭或一致备份，不能漏掉WAL。

能力边界：

- 已保存原文/有效OCR修订、成功译文、音频、回放和导出优先互读，打开不推理。
- 文字/字幕续译要求实际模型digest、recipe、分段和binding兼容，沿保存计划只处理未完成项；不保证GPU平台变化后新生成文字逐字一致。
- 跨MLX/MPS与CUDA的识别检查点不能默认续跑。缺相同backend/resource身份或兼容证明时拒绝原任务识别继续，保留读取/导出；用户明确重新识别时另建任务并引用原音频，不覆盖成功字幕。
- 旧封存代码/source与历史唯一材料只读；新Windows实现和模型格式转换在独立目录，记录差异与兼容条件。

## 7. 安装、服务生命周期和发行

每平台单独固定软件包、来源、hash、平台/架构、依赖/许可和真实下载/解压大小。Mac继续DMG主/ZIP备用；Windows优先用户级安装器（具体MSI/EXE形式经原型确定）及ZIP备用，解释器和必要运行库受管理，模型/config/词表/VAD数据仍外置。

Windows运行包须具备独立Python、固定CUDA依赖和所需VC运行库；实际依赖决定是否捆绑/检查可再分发组件。不依赖用户全局Python/Conda、开发SDK或任意系统PATH，显卡驱动作为硬件前提单独说明。

Ollama优先复用兼容现有本机服务，Windows官方产物单独固定与验证，不把Mac0.35.0 zip用于Windows。专用服务所有权和活动请求保护采用相同规则，平台进程/端口证明各自实现；共享服务不停止/卸载模型，不修改全局配置，不暴露局域网，不引入云推理。

安装锁、操作身份、可信校验、受控解压、原子激活/回退和任务隔离保持。Windows防病毒占用、DLL加载、大小写/重解析点、磁盘空间、被打开文件无法替换、异常结束与重开均是新验收场景；卸载/修复默认保留用户任务和外部模型。

Mac签名/系统提示和Windows Authenticode/SmartScreen分别说明。个人自用阶段不自动购买证书或新增公证目标，也不以关闭保护/去安全标记冒充正常安装。二进制公开上传须资产完成后单独授权；源码推送不等于二进制发布。
